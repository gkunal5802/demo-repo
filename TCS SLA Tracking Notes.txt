1. At TCS, I worked on a multi-tenant asset management and monitoring platform for multiple client accounts.

2. The platform was primarily responsible for tracking assets, monitoring SLA compliance, and generating billing information based on asset usage and SLA-related events.

3. The system followed a microservices architecture where different business capabilities such as Asset Tracking, SLA Monitoring, and Billing were implemented as independent services.

4. One of the important design decisions was to make the services loosely coupled using Apache Kafka. For example, whenever an asset's status changed, the Asset Tracking service published an event to Kafka. The SLA service consumed those events to evaluate SLA conditions, while the Billing service could independently consume relevant events for usage and billing calculations. This allowed the services to scale independently and reduced direct dependencies between them.

5. One of the key features that we maintained was an append-only history of asset status changes at the database level. Instead of updating the previous status record, every status transition was stored as a new record. This gave us a reliable audit trail that could be used for SLA calculations and billing.

6. For performance and concurrency, we used Redis for frequently accessed asset-status data and distributed locking to make sure that when multiple scheduler instances were running, the same SLA breach wasn't processed multiple times.

7. At gateway, we also implemented API security using Spring Security with JWT and role-based access control, along with request validation and rate limiting.

Towards the end, I worked on automating monthly billing reports by aggregating asset usage and SLA compliance information from event data. This reduced a significant amount of manual report preparation.

My primary responsibility was backend development of MVC architecture, schema designing and implementing REST API using Java, Spring Boot, Spring Security, and PostgreSQL.
Overall, my role was primarily focused on backend development, distributed-system design, API development, data modeling, concurrency handling, and making the services reliable and scalable.

* Asset tracking Module:
This is the service that client will directly interact with and configure. This module provides features like asset registration, status transitions for assets, with full history logging associated with each client. The access to this service is only provided to admin for configuration purposes. The service tracks the asset status change and publishes event to all the downstream services like SLA Compliance service and Billing services.

* SLA Monitoring Module:
This service is responsible for maintaining and calculating SLA breaches. It Continuously checks for the asset status change via scheduled jobs and scans open assets elapsed times against SLA rules. these rules are configured by client only (different for each asset category).

* Billing Module:
It periodically (monthly, via scheduled job) aggregates asset usage + SLA compliance per client and generates a report file. Billing reports tie directly back to SLA breach data, so if a client had 3 breaches in a category with a penalty clause, that's reflected in the final billed amount — the report is auditable back to the individual breach events.
