# Consistent Hashing

**Consistent hashing** is a technique used in distributed systems to distribute data across a changing set of servers (or nodes) while minimizing how much data needs to move when servers are added or removed.

## The Problem with Traditional Hashing

Suppose you have 4 cache servers and assign keys using:

```text
server = hash(key) % 4
```

If you add a 5th server:

```text
server = hash(key) % 5
```

Now almost every key maps to a different server, causing massive data reshuffling.

## How Consistent Hashing Works

Instead of mapping keys directly to servers:

1. Imagine a circular hash space (a "hash ring").
2. Hash each server onto the ring.
3. Hash each key onto the same ring.
4. A key is assigned to the first server encountered when moving clockwise around the ring.

Example:

```text
        Server A
            |
            v
     +-------------+
     |             |
Server C         Server B
     |             |
     +-------------+
```

If a key hashes between Server A and Server B, it belongs to Server B.

## Adding a New Server

Suppose Server D is added between A and B:

```text
A ---- D ---- B ---- C
```

Only the keys that previously belonged to B and now fall between A and D need to move.

Instead of moving nearly all keys, only a small fraction is reassigned.

## Removing a Server

If Server B fails:

```text
A ---- D ---- C
```

Only B's keys are redistributed (typically to the next clockwise server).

## Virtual Nodes (VNodes)

Real systems usually place multiple virtual copies of each server on the ring:

```text
A1, A2, A3
B1, B2, B3
C1, C2, C3
```

Benefits:

* Better load balancing
* Less risk of uneven distribution
* Easier scaling

## Example Use Cases

* Distributed caches (e.g., Memcached clusters)
* Distributed databases
* Content delivery networks (CDNs)
* Distributed key-value stores like Apache Cassandra and Amazon Dynamo
* Load balancing systems

## Complexity

With servers stored in a sorted structure:

* Lookup: **O(log N)**
* Add/remove server: **O(log N)**
* Data movement on node change: approximately **1/N** of keys

## Intuition

Think of consistent hashing as placing both **data** and **servers** on a circle. When the set of servers changes, only the nearby portion of the circle is affected, so most data stays where it is. This makes it ideal for large-scale distributed systems where servers frequently join or leave the cluster.

## Comparison

| Feature                     | Traditional Hashing  | Consistent Hashing  |
| --------------------------- | -------------------- | ------------------- |
| Lookup Speed                | O(1)                 | O(log N)            |
| Implementation              | Simple               | Complex             |
| Node Addition               | Almost all keys move | ~1/N keys move      |
| Node Removal                | Almost all keys move | ~1/N keys move      |
| Load Balancing              | Good initially       | Needs virtual nodes |
| Scalability                 | Poor                 | Excellent           |
| Used in Distributed Systems | Rarely               | Very common         |


## Disadvantages:

Consistent hashing solves the **data redistribution problem**, but it comes with several trade-offs.

## 1. Uneven Data Distribution (Hotspots)

Without virtual nodes, servers may not be evenly spaced on the hash ring.

Example:

```A ---------------------- B -- C```

* Server A owns most of the ring.
* Server B and C own very little.

Result:

* Uneven storage usage
* Uneven CPU/network load

**Solution:** Use **virtual nodes (vnodes)**. i.e. make replicas of servers.

## 2. Hot Keys Still Cause Imbalance

Even if keys are evenly distributed, traffic may not be.

Example:

```text
user:123 -> 1 request/sec
user:999 -> 100000 requests/sec
```

If the hot key lands on one server:

```text
Server A -> normal load
Server B -> overloaded
Server C -> normal load
```

Consistent hashing balances **number of keys**, not necessarily **request volume**.

## 3. More Complex Than Simple Hashing

Traditional hashing is very simple: ```server = hash(key) % N;```

Consistent hashing requires:

* Hash ring maintenance
* Sorted server positions
* Clockwise lookup
* Node addition/removal logic
* Replication handling
* Virtual node management

This increases implementation complexity.

## 4. Lookup Overhead

- Traditional hashing: takes ```O(1)```
- Consistent hashing: takes ```O(log N)``` to find next server on ring using a balanced tree or sorted map. Usually not a big issue, but it is more expensive.

## 5. Data Movement Still Exists

When a node joins or leaves ```Only ~1/N keys move``` which is much better than moving nearly all keys.

However:

* Large clusters (100TB) may store TBs of data.
* Even moving 5–10% of data can be expensive.

Example:
```text
100 TB cluster
10 servers

Add one server
≈ 10 TB may need migration
```

## 6. Poor Handling of Heterogeneous Servers

Suppose:

```text
Server A = 64 GB RAM
Server B = 8 GB RAM
Server C = 128 GB RAM
```
Basic consistent hashing treats them equally.

Result:
* Small server gets same share as large server.

**Solution:**
Assign more virtual nodes to stronger machines.

Example:
```text
A -> 64 vnodes
B -> 8 vnodes
C -> 128 vnodes
```

This is called **weighted consistent hashing**.


## Basic Interveiw Questions

## 1. What problem does consistent hashing solve?
* Minimizes data movement when nodes are added/removed.
* Useful for distributed caches, databases, load balancers.

## 2. Why can't we simply use `hash(key) % N`?
* Changing N remaps almost all keys.
* Causes massive data migration.

## 3. How does consistent hashing work?
* Hash servers onto a ring.
* Hash keys onto the same ring.
* Assign key to first clockwise server.

## 4. What happens when a server is added?
* New server takes ownership of a portion of its successor's keys.
* Only ~1/N data moves.

## 5. What happens when a server is removed?
* Its keys move to the next clockwise server.
* Only keys owned by that server are affected.

## 6. Why does only O(K/N) data move?

## 7. What is the expected ownership of each node on the ring?
```1/N``` of the hash space.

## 8. Compare data movement between modulo hashing and consistent hashing.
* Modulo hashing: ~100% remapping.
* Consistent hashing: ~1/N remapping.

## 9. Is data distribution always uniform?
Answer: No. Servers may hash unevenly.
```A----------------------B--C```

A gets most keys.

## 10. How do you solve uneven distribution?
**Virtual Nodes (VNodes).**

## 11. What are Virtual Nodes?
Each physical machine appears multiple times on the ring.

Example:

```text
A1 A2 A3
B1 B2 B3
C1 C2 C3
```
Improves load balancing.

## 12. How many virtual nodes should be used?
* Depends on cluster size.
* Typically 100–200+ per machine.
* Tradeoff between balance and metadata overhead.

## 13. Where is consistent hashing used?
* Apache Cassandra
* Amazon Dynamo
* Memcached clusters
* Distributed caches
* Distributed databases
* CDNs

## 14. How do you find the next server on the ring efficiently?

* Sorted array
* Balanced BST
* TreeMap (Java)
* std::map (C++)

Lookup: ```O(log N)```

## 15. What data structure would you use to implement a hash ring?

```std::map<uint64_t, Node>``` for cpp
or
```TreeMap<Long, Node>``` for java

## 16. What hash functions are commonly used?
* MD5
* SHA-1
* MurmurHash
* xxHash

Need:
* Uniform distribution
* Fast computation

## 17. What happens if a node suddenly dies?
* Keys move to successor node.
* Replicas take over if replication exists.

## 18. How is replication handled?

```text
Primary: Node A
Replica1: Node B
Replica2: Node C
```
Store on next R nodes clockwise.
## 19. How do you ensure high availability?
* Replication
* Multiple data centers
* Failure detection
* Automatic rebalancing

## 20. What happens during rebalancing?
* Data copied to new owner.
* Metadata updated.
* Old copies eventually removed.

## Advanced Questions

## 21. What is weighted consistent hashing?

Suppose:

```text
Server A = 64 GB
Server B = 8 GB
Server C = 128 GB
```
Assign more virtual nodes to larger servers.

## 22. What is the hotspot problem?

One key receives huge traffic: ```user123 -> 1M req/sec```

Even perfect hashing cannot balance it.

Solutions:

* Replication
* Request splitting
* Caching

## 23. Can consistent hashing guarantee equal load?
No. It balances probabilistically.

## 24. What are the disadvantages of consistent hashing?
* More complex
* O(log N) lookup
* Uneven distribution without vnodes
* Rebalancing cost
* Hot key problem

## 25. How does Cassandra use consistent hashing?

## Very Advanced Questions (Senior/Staff Level)

## 26. Difference between Consistent Hashing and Rendezvous Hashing?

Expected:

* Both minimize remapping.
* Rendezvous hashing often simpler.
* No ring required.
* Better distribution in some scenarios.

## 27. What is Rendezvous (Highest Random Weight) Hashing?

For each key:

```text
score(node,key)
```

Choose highest score.

No ring needed.
